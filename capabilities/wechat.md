# WeChat Official Account

## CLI boundary

The CLI can check Official Account API access and turn Markdown into one inline-styled `article_type=news` draft: it uploads the required cover and local body images, rewrites image URLs, and calls `draft/add`. It never calls `freepublish/*` or `message/mass/*`.

The agent prepares the article and assets, configures fixed egress, runs dry-run, and creates the draft. Successful uploads followed by a successful `draft/add` response with a nonempty native `media_id` verify draft creation. The human provisions credentials, QR-authorizes IP allowlist changes, and makes any later publication decision in the official console. The CLI does not design, crop, resize, compress, or deduplicate covers.

## Authentication

WeChat uses `WECHAT_APP_ID` and `WECHAT_APP_SECRET` over the Official Account API, not a browser profile. Every call must use one stable, allowlisted egress configured with either `WECHAT_SSH_TUNNEL` or `WECHAT_PROXY_URL`; a short-lived stable token is cached locally and may be renewed automatically.

Accepted forms are `WECHAT_SSH_TUNNEL=[user@]host[:port]` or `WECHAT_PROXY_URL=socks5://[user:pass@]host:port` (also `http://` or `https://`). Set exactly one, using a host whose public IP is stable.

Provision credentials at `https://developers.weixin.qq.com/platform/`, configure one stable egress, then run `publish wechat check`. If it returns `40164`, add the exact egress IP reported by WeChat to IP白名单 with an admin QR scan, then rerun the check. Do not guess the proxy endpoint's outbound IP.

Authentication can fail because credentials are missing or rejected, token exchange fails, error `40164` reports an egress IP absent from IP白名单, the SSH tunnel/proxy or network fails, or the API response is inconclusive. There is no allowlist-edit API: a human must add the reported IP in the developer console and approve it by QR scan.

## Platform specification and gotchas

- Supply exactly one of `--from` or `--text`. For file/stdin input, an optional leading empty or YAML mapping frontmatter block is metadata only and is removed before rendering. Recognized string keys are `title`; `author`; `description`/`summary`/`digest`; `coverImage`/`cover`/`image`; and `sourceUrl`/`contentSourceUrl`/`source_url`; flags override metadata and other keys are ignored. BOM and LF, CRLF, or lone-CR delimiters are recognized. Mapping-intent malformed or unterminated frontmatter exits 2 before `--out`, token exchange, uploads, or API access. Valid scalar/sequence blocks and thematic-break prose remain literal Markdown apart from a leading transport BOM. Inline `--text` is always literal and is never interpreted as frontmatter.
- Title resolves from `--title`, file/stdin frontmatter, or the leading H1. A cover resolves from `--cover` or file/stdin frontmatter and is required. Relative frontmatter/body-image paths resolve beside a Markdown file (or from the invocation directory for stdin); a `--cover` flag resolves from the invocation directory.
- Author resolves from an explicit `--author`, then a nonblank string `author` in validated file/stdin frontmatter, then `WECHAT_AUTHOR`, then empty. Values are trimmed. An explicitly supplied blank or whitespace-only `--author` intentionally clears the lower-precedence values; blank, whitespace-only, and non-string frontmatter authors are ignored and fall through.
- Documented limits are title 32 字, author 16 字, and digest 120 字, but exact Unicode measurement is unknown and server-authoritative. Conflicting HTML-size documentation also makes the effective body limit unknown.
- The renderer uses inline `style=` because WeChat strips stylesheets and classes. Caller raw HTML is unsupported: block or inline HTML (including nested list, quote, table, tag attributes, and comments) exits 2 instead of being passed through. Write HTML-looking text with escaped angle brackets/entities or inside a code span/block. This recursive token check runs before cover/body-image reads, rendered inspection, `--out`, token/client imports, uploads, or API access.
- Body paragraphs use 16px text, 1.75 line height, and 44px bottom margin: the previous 16px gap plus one 28px blank body line. Reference entries retain compact 2px spacing. This is rendered inline CSS; canonical Markdown is unchanged.
- Rendered Markdown links allow explicit `http://`, `https://`, `mailto:`, relative URLs, and fragments. Inside a recognized authored bibliography, safe hyperlinks become readable labels. Outside that section, safe links to `mp.weixin.qq.com` and safe non-HTTP(S) links stay inline; other HTTP(S) links become bottom citations. `--keep-links` retains all safe inline anchors but does not make unsupported hyperlinks clickable. Markdown images allow explicit HTTP(S) URLs or local filesystem paths; `sourceUrl`/`--source-url` requires an absolute explicit HTTP(S) URL. Mixed-case safe schemes, IPv6/ports, ordinary internal spaces in angle-bracket relative paths, and drive-absolute Windows image paths work. UNC/network image paths, HTTP(S) userinfo, leading/trailing Unicode whitespace, active/unknown schemes (`javascript:`, `data:`, `vbscript:`, `file:`), control/entity/percent-obfuscated schemes, malformed absolute/backslash forms, and scheme-relative destinations are rejected locally before assets or platform access, including destinations whose hyperlink markup would be removed.
- An authored bibliography starts at a top-level Markdown heading of any depth whose visible text is exactly `Reference`, `References`, `Bibliography`, `参考文献`, or `参考资料` (English is case-insensitive; inline formatting is allowed). After optional blank lines, it must contain at least one paragraph beginning with `【N】` or `[N]` and reference text, or a Markdown ordered/bullet list. Consecutive such entries and blank lines belong to the section; the first other block or any heading ends it. Put following creation/completion dates in a separate, unnumbered paragraph. A continuation within an entry paragraph or list item belongs to that entry. Headings nested in quotes/lists, arbitrary prose headings, and matching headings without adjacent entries do not establish a bibliography. More than one populated recognized section exits 2 with `wechat_bibliography_ambiguous`; combine the entries under one reference heading in the staging copy.
- With one recognized bibliography, the renderer preserves original reference numbers, ordered-list number gaps, grouped sources, authors, titles, dates, and nested inline formatting. By default, it removes hyperlink markup and hidden destination URLs within that section while retaining each readable label; those links add no superscripts or generated citations. Repeated destinations remain in their authored entries without renumbering or deduplication. Explicitly authored visible URLs, including bare GFM `www.example.com` autolinks, remain visible text without adding hidden destinations. Canonical Markdown and source links remain unchanged locally. The dedicated reference section uses a top divider, 14px heading, and compact 13px entries with 2px paragraph/item spacing. `--keep-links` preserves safe hyperlinks as well as this compact styling. The authored reference section moves after all body blocks in the rendered HTML. Following non-reference blocks, including separate 起笔于/完成于 paragraphs, keep their relative order and ordinary body styling before the references. Words such as 起笔 or 完成 inside an entry do not split or move that entry. Any generated body-link citations follow the authored bibliography, so all references remain at the end.
- Reference hyperlinks do not generate citations. External body links retain their existing behavior: repeated destinations share a superscript number and an entry in the generated References footer. When no authored reference section is recognized, this default citation behavior applies throughout the article.
- Every generated dynamic HTML attribute is escaped. Local body images retain a separate exact parser/path identity so escapable filenames and duplicates keep caller order through upload and CDN-URL rewriting; no caller path is emitted as raw markup.
- Documented cover formats are BMP, PNG, JPEG/JPG, and GIF with a `10M` label. WeChat offers 2.35:1 and 1:1 cover crops; these are crop choices, not proven required input ratios.
- Local body images use JPG or PNG with documented wording `1MB以下`. Exact byte, dimension, count, recompression, and quota boundaries remain server-authoritative.
- Before any API/token access, every cover and local body-image path must be a readable regular file with recognized magic/header bytes, positive dimensions readable from its header, and a filename extension matching the detected type. Header-invalid, dimension-unreadable, and extension-mismatch inputs are rejected locally; covers then allow BMP/GIF/JPEG/PNG, while body images allow only JPEG/PNG. Renaming a file does not convert it.
- Draft completion uses the API receipt after local validation and required uploads succeed. Opening the draft or a gated URL, console login, and visual inspection are not completion steps. An API-verified draft is complete even when its URL is inaccessible; the receipt does not claim publication.
- Original declaration and creation source are separate console settings. The documented public `draft/add` article schema has no fields for 原创声明 or 创作来源; `author` and `content_source_url` do not set them. The CLI does not set or verify either declaration, and its success receipt explicitly identifies that limit. Do not add guessed fields, private console endpoints, or a second CLI transport to simulate support. See the [official draft/add schema](https://developers.weixin.qq.com/doc/subscription/api/draftbox/draftmanage/api_draft_add.html).
- For an operator-authored opinion draft, the calling workflow should enable 原创声明 and choose 创作来源 → 个人观点，仅供参考. This is a console handoff after API draft creation: the operator or an agent with authorized browser access opens the existing matching draft under 内容管理 → 草稿箱, checks the visible title/body, completes the original-declaration controls offered by the live UI, selects that exact creation-source label, and saves the draft. Verify both settings persisted before reporting them complete; if either control is unavailable, requires a human-only login/QR step, or does not persist, report the specific pending setting and hand off. Do not infer originality from an author name, HTML text, or `media_id`, and do not apply an original declaration to a reprint. The API draft remains verified even if this separate metadata step is pending; reuse it rather than creating another draft. This handoff is guidance, not a live-verified CLI browser capability, and grants no final-publication authorization.
- If the agent cannot set and verify both declarations for the original opinion draft, it must identify the pending settings in its handoff and explicitly remind the receiving human: **发表前，请在现有草稿中开启原创声明，并将创作来源设为「个人观点，仅供参考」；保存后确认两项设置均已生效，再发表。** Do not leave this as an implicit console task or report the declarations complete without evidence. This before-publication reminder does not change the verified API draft status or authorize publication.
- Human terminal output is a presentation-only projection of the same closed, recursively frozen article/image snapshot used for uploads and `draft/add`. Caller lines are visibly framed; terminal/layout controls and literal backslashes have unambiguous visible spellings. Each field and the whole command transcript are bounded; truncation reports exact original UTF-16 size plus SHA-256 over the complete unnormalised UTF-8 scalar string. Unpaired surrogates or an invalid projection exit 2 before `--out`, token/client creation, upload, or API staging. Canonical inline HTML, metadata, source URL, and image paths are not rewritten by terminal projection.
- `publish wechat draft ... --json` emits exactly one `publish.transport-receipt/v1` document; the human summary uses the same frozen facts. It records ordered cover/body-image requested, resolved, uploaded, observed, and verified stages. If a later step fails, returned permanent-material/CDN references remain explicit remote residue; a failed or ambiguous `draft/add` never erases earlier uploads or claims publication. Server failures carry only bounded, redacted stage/code/status/message evidence and never trigger automatic rewriting or retry.
